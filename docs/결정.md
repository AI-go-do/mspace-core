## 1. 겹침은 DB 제약으로

- **고른 것:** `no_room_overlap`(EXCLUDE), `one_active_per_owner`(부분 유니크), `no_person_overlap`. 서버 검사는 친절한 400용
- **이유:** 서버에서 조회 후 저장만 하면 동시 요청이 둘 다 통과함. 측정: 제약 없는 버전 5번 모두 중복, 제약 버전 100건 중 1건만 ([트러블슈팅 1](트러블슈팅.md#1-동시-100건에서-중복-예약-112))
- **버린 것:** 서버 검사만 (빠르지만 동시성에 약함), 앱 메모리 잠금 (서버 2대 이상이면 안 맞음)

## 2. 교착은 줄 세우기 잠금 + 다시 하기

- **고른 것:** `pg_advisory_xact_lock`(방 → 사람 id 순) + 최대 3번 다시
- **이유:** 다시 하기만으로는 503 69건·70초. 잠금으로 순서를 맞추면 기다렸다가 409로 끝남
- **버린 것:** 다시 하기만, 테이블 전체 잠금 (다른 방 예약까지 줄 섬)
- **병목:** 같은 방·같은 사람끼리만 줄을 서고, 다른 방은 서로 기다리지 않음

## 3. 이름은 재웅 명세 기준

- `users`, `rooms`, `CANCELED`, `AUTO_CHECKED_OUT`, `access_code`. 팀이 이미 명세를 보고 있어서 맞춤

## 4. 로그인 전 개발용 헤더

- `X-User-Id`는 `mspace.auth.dev-header=true`일 때만 받음. 로그인(#37)이 들어온 뒤에도 토큰이 있으면 토큰만 봄. 운영에서는 꺼요

## 5. 커버리지 게이트는 SonarQube

- 팀원들처럼 팀 공용 SonarQube 품질 게이트로 막고, JaCoCo는 보고서만 만듦 (지영 결정)

## 6. 잠금 대기 3초 상한

- **이유:** 무제한이면 몰릴 때 요청이 계속 쌓임. 상한은 **시도 한 번마다 3초**이고, 넘으면 처음부터 다시 함(최대 3번). 3번 다 넘으면 503 `RESERVATION_BUSY`로 "잠시 후 다시"를 안내. 그래서 한 요청의 최악 대기는 약 9초 ([트러블슈팅 4](트러블슈팅.md#4-잠금-대기-상한이-잠금마다-따로-걸림-113-coderabbit-지적))
- 숫자는 설정값 `mspace.reservation.lock-timeout`

## 7. 같은 멱등 키는 처음 예약을 200으로

- **이유:** 비서가 응답을 못 받아 다시 보내도 예약이 두 번 생기지 않고, 받은 쪽은 같은 결과를 봄. 내용이 다르면 409 `IDEMPOTENCY_KEY_REUSED`
- 키는 `(owner_id, idempotency_key)` 유일 (V2)

## 8. 즉시 시작은 버튼 누른 시각부터

- 끝은 30분 칸으로 올림(14:17 → 최대 16:30), 10분 안에 키패드 입실 안 하면 노쇼. 요구사항 v0.4·DB 기준과 맞춤 (10/30 키패드 입력 기준은 버림)

## 9. 미입실 정리는 1분 주기 + 만들기 직전

- **이유:** 1분만 기다리면 끝나자마자 다시 잡을 때 끝난 내 예약 때문에 409가 남. 만들기 직전에도 한 번 돌림
- 조건부 UPDATE라 여러 번 돌아도 안전하고, 실패해도 예약 만들기를 막지 않음 ([트러블슈팅 9](트러블슈팅.md#9-정리가-실패하면-예약-만들기까지-실패-113))

## 10. 연장하기 1회 (11/3 팀 결정, 요구사항 FR-RSV-105)

- 오전에는 "연장 없음, 끝난 뒤 새 예약 + 새 번호"였지만, 영준과 합의해 **"연장하기" 1회**로 바꿈
- **이유:** 방 안에 있는데 바깥 키패드에 새 번호를 넣어야 하는 불편, 그 사이 노쇼로 풀리는 문제
- 1회를 넘기면 409 `RESERVATION_EXTENSION_LIMIT`

> 상태: 코드는 PR #51(리뷰 중, #45 다음에 머지)

- **고른 것 (11/4, docs FR-RSV-105 기준):** 한 트랜잭션에서 지금 예약 퇴실(조건부 UPDATE) → 누른 시각부터 새 예약을 바로 `IN_USE`로 INSERT(`continued_from_id`). 새 예약이 실패하면 퇴실도 롤백
- **순서가 퇴실 먼저인 이유:** 겹침·대표자 1건 제약은 문장마다 바로 검사돼서, 새 예약을 먼저 넣으면 지금 예약과 겹쳐 409
- **"최대 2시간"은 늘리는 시간 기준 (11/4 지영):** docs 문장 "endAt은 지금 종료 + 30분 단위, 최대 2시간" 그대로. 그래서 새 예약은 최대 2시간 10분(13:50 → 16:00)이고, DB에는 즉시 시작 규칙(`is_instant`, 2시간 30분 미만)으로 넣음. 버린 것: 새 예약 길이 기준(10분 전에 누르면 1시간 30분만 늘어서 화면 칩이 들쭉날쭉)
- **우회 막기:** 연장까지 쓴 뒤 30분 안에 같은 대표자가 새로 잡으면 이어진 사용으로 보고 예약 만들기도 409. 거슬러 올라가며 세는 쿼리라 `(owner_id, end_at)` 인덱스를 V7에 넣음
- **동시성:** 동시 10번 → 201 1개, 409 9개. 조건부 UPDATE가 한 번만 통과하고, 마지막은 `one_continuation_per_reservation`(부분 유니크)이 막음
- **오류 코드 하나 추가:** 시간 밖(종료 10분 전보다 이르거나 종료 지남)은 409 `RESERVATION_EXTENSION_NOT_OPEN`. 화면이 "언제부터 되는지"를 따로 안내할 수 있게 1회 제한과 나눔

## 11. 비서 예약 표시는 `X-Created-Via` 헤더

> 상태: 코드는 PR #45(리뷰 중). 머지 전 develop은 모든 예약을 WEB으로 저장해요

- **고른 것:** 비서가 `X-Created-Via: AGENT`를 붙이면 `created_via = AGENT`, 없으면 WEB, 다른 값은 400 (대소문자·앞뒤 공백 무시)
- **이유:** 지금 바로 되고 로그인 코드를 안 건드림. 건수 구분용이라 거짓으로 붙여도 권한은 늘지 않음
- **버린 것:** JWT scope (믿을 만하지만 로그인 토큰 발급을 바꿔야 함). 비서 권한 제한이 필요해지면 그때 scope로
- **400인 이유:** 오타("agnet")를 WEB으로 세면 비서 숫자가 조용히 틀어짐
- **이름 (11/4 지영 결정):** 처음엔 `X-Client: agent`로 만들었다가 영준 이슈 #43 제안대로 `X-Created-Via`로 바꿈. DB 칸 `created_via`와 같은 이름이라 뜻이 바로 보이고, 비서 쪽 코드에 아직 없어서 고칠 게 없었음. 버린 것: `X-Client`("어떤 앱이 보냈나"로 더 넓게 쓸 수 있지만 지금은 그 용도가 없음)

## 12. 건수 조회는 관리자만

> 상태: 코드는 PR #45(리뷰 중). `users.role`(V6)과 `GET /api/reservations/stats`는 #45가 머지돼야 develop에 생겨요

- **이유:** 개인정보는 없지만 운영 숫자라 학생에게 열 이유가 없음 (지영 결정)
- 명세 Q-06의 `role = ADMIN`을 `users.role`(V6)로 처음 넣음. 신고 판정·관리자 화면도 같은 칸을 씀
- **성능:** 부를 때만 `GROUP BY` 한 번. 방 5개라 한 달 수천 줄이어서 `created_at` 인덱스는 아직 안 넣음

## 13. 끝나지 않은 예약 1건을 참여자에게도

> 11/5 지영 결정, docs v0.4.9 FR-RSV-003

- **계기:** 지영이 개발 서버에서 참여자로 15–17시 예약이 있는 상태에서 대표자로 19–21시 예약을 잡았더니 통과함. 원래 docs는 "참여자는 횟수 제한 없음, 같은 시간 두 방만 금지"라 버그는 아니었음
- **고른 것:** 참여자 표(`reservation_participant`, 대표자도 들어 있음)에 부분 유니크 인덱스 `one_active_per_member (user_id) WHERE active`. 걸린 사람이 대표자 본인이면 `OWNER_HAS_ACTIVE_RESERVATION`, 다른 참여자면 `PARTICIPANT_HAS_ACTIVE_RESERVATION`(누구인지 안 알려 줌)
- **이유:** `active`는 트리거가 예약 상태(BOOKED·IN_USE)에 맞춰 이미 관리하고 있어서 인덱스 하나로 끝남. 서버에서 조회 후 막으면 동시 요청이 둘 다 통과함(1번 결정과 같은 이유). 측정: 같은 참여자 2명을 넣은 100팀이 다른 방·다른 시간으로 동시 요청 → 201 1건, 409 99건
- **버린 것:** 서버 조회 검사(동시성에 약함), 트리거로 검사(인덱스보다 느리고 코드가 늘어남)
- **동시성:** 줄 세우기 잠금(2번)이 이미 참여자 id 순으로 잡혀서 교착 없이 한 줄로 섬
- **인덱스 영향:** 끝나지 않은 줄만 들어가는 작은 인덱스. 참여자 줄 INSERT·상태 변경 때 한 번 더 갱신됨
- **영향:** 이미 다른 예약이 있는 친구는 참여자로 못 넣음. 연장하기는 퇴실 먼저라 그대로 됨(10번)
- **배포 주의:** 규칙 전에 만든 데이터에 한 사람이 끝나지 않은 예약 2건 이상에 들어가 있으면 V13이 멈춤. 마이그레이션이 데이터를 마음대로 취소하지 않고, 걸리는 회원·예약 id를 오류 메시지로 알려 줌(코드래빗 #64 지적)
  - 미리 보기: `SELECT user_id, array_agg(reservation_id) FROM reservation_participant WHERE active GROUP BY user_id HAVING count(*) > 1;`
  - 정리: 시작 전 예약은 대표자가 취소, 사용 중이면 퇴실, 아니면 예약이 끝나 자동 정리(노쇼·자동 퇴실)된 뒤 다시 배포. 어느 예약을 남길지는 사람(대표자·운영자)이 정함

## 14. 사진은 core DB에 저장 (11/5 지영 "추천대로")

- **고른 것:** 사진 파일 자체를 `reservation_photo.data`(bytea)에 담음. 1장 2MB, 종류별 1장, 30일 뒤 지움
- **이유:** 새 서버·라이브러리·배포 설정 없이 바로 되고, 예약과 같은 DB라 "예약은 지웠는데 파일은 남음" 같은 어긋남이 없음. 백업도 DB 하나로 끝
- **버린 것:** 서버 폴더에 파일 저장(컨테이너를 다시 만들면 사라져서 볼륨 설정이 필요), MinIO 같은 저장 서버(가장 확장성 좋지만 서버 하나를 더 띄워야 함)
- **확장:** 저장은 `PhotoPort` 뒤에 있어서, 사진이 많아지면 어댑터만 바꿔 저장 서버로 옮김. 그때 이 표는 주소만 남김
- **성능:** 방 5개 × 하루 몇 건 × 2장 × 30일이면 많아야 수천 장, 몇 GB 안. 목록 조회는 `data`를 읽지 않음. 지우기는 `created_at` 인덱스
- **보안:** 형식은 브라우저가 보낸 Content-Type이 아니라 파일 앞부분으로 판단. 볼 때 `nosniff`·`no-store`. 남이 보면 404(있는지도 안 알려 줌)
- **기존 행:** V1 표에 쓰는 API가 없어 빈 표여야 함. 그래도 행이 있으면 V14가 데이터를 건드리지 않고 멈춤(사진 자체가 없어 새 칸을 채울 수 없음). 그때는 `SELECT * FROM reservation_photo`로 보고, 지울지 정한 뒤 다시 배포

## 15. 참여자는 서로 수락한 친구만 (11/6 지영 결정)

> FR-RSV-004 변경. docs 반영 PR 따로

- **계기:** 학번만 알면 모르는 사람도 참여자로 넣을 수 있었음. 그 사람은 동의 없이 예약에 묶이고, 끝나지 않은 예약 1건(13번) 때문에 자기 예약도 못 잡게 됨
- **고른 것:** 학번으로 친구 요청 → 받은 사람이 수락하면 친구. 친구는 삭제할 때까지 계속 남음. 예약 참여자는 친구만(아니면 `403 PARTICIPANT_NOT_FRIEND`, 누가 아닌지는 안 알려 줌). 표 `friendship`(V15), 한 쌍에 줄 하나(`one_friendship_per_pair`, least·greatest)
- **이유:** 한 번만 동의하면 계속 같이 예약할 수 있어 편하고, 모르는 학번 문제를 막음
- **버린 것:** 한쪽만 추가(상대 동의가 없어 문제가 그대로), 예약마다 초대 수락(가장 안전하지만 "수락 전" 예약 상태가 생겨 노쇼·겹침 규칙이 복잡해짐)
- **동시성:** 서로 동시에 요청하면 UNIQUE 인덱스가 하나만 넣고, 늦은 쪽은 상대 요청을 보고 수락으로 처리. 10번 동시 → 매번 줄 하나·친구. 수락·거절·취소는 조건부 UPDATE/DELETE라 두 번 눌러도 한 번만
- **인덱스 영향:** 쌍 유니크 1개 + 요청자·받는 사람 인덱스 2개. 예약 만들 때 친구 확인 쿼리 1번 추가(참여자 많아야 7명)
- **영향:** 친구를 삭제해도 이미 잡은 예약의 참여자는 그대로. 화면에 친구 창이 붙기 전에는 `MSPACE_FRIENDS_ONLY=false`로 끌 수 있음(기본 켜짐). 다른 예약 테스트는 테스트 설정에서 끄고, 친구 규칙은 FriendApiTest가 켜고 봄
- **남은 것:** 요청을 많이 보내는 사람 막기(횟수 제한)는 없음. 이름은 친구끼리도 가린 이름(김*영)

## 16. 알림 읽음은 `read_at` 한 칸으로 (11/6)

> FR-NTF-103 "안 읽은 알림은 점 표시". 표는 V10에 이미 `read_at`이 있어서 마이그레이션 없음

- **고른 것:** 하나 읽기 `POST /api/notifications/{id}/read`(204), 모두 읽기 `POST /api/notifications/read-all`, 안 읽은 개수 `GET /api/notifications/me/unread-count`
- **이유:** 상태 변경은 `POST /{id}/<동사>`(팀 컨벤션). 개수 API를 따로 둔 건, 종 아이콘 점은 홈 화면마다 불려서 목록 50개를 다 받는 것보다 가볍기 때문
- **두 번 눌러도:** `read_at = coalesce(read_at, now)` 조건부 UPDATE 한 문장이라 처음 읽은 시각이 남고 204가 그대로 나감

- **동시성:** 모두 읽기 도중에 새 알림이 들어오면, 커밋 순서에 따라 새 알림은 안 읽음으로 남음(맞는 동작)
- **인덱스 영향:** 새 인덱스 없음. 개수는 `notification_user_recent (user_id, created_at DESC)`로 내 줄만 훑음. 한 사람 알림이 수천 개로 늘면 `WHERE read_at IS NULL` 부분 인덱스를 검토
- **남은 것:** 오래된 알림 지우기(보관 기간)는 없음

## 21. 관리자 기간 막기 (11/9 지영)

> Q-23, core #95. 공사·점검·대관으로 방을 일정 기간 못 쓰게 함. 번호 20은 core #97(관리자 센서 API)

- **막는 곳:** 예약 저장(`JdbcReservationAdapter.insert`) 한 곳에서 확인 → 미리 예약·즉시 시작·연장이 모두 409 `ROOM_BLOCKED`
  - 이유: 세 길이 모두 이 insert를 지남. 서비스마다 따로 넣으면 하나를 빠뜨리기 쉬움
  - 안내 문장에 사유와 끝 시각("점검 중이라 3/5 14:00까지 예약할 수 없습니다")
- **동시성:** 막기 저장도 예약 저장과 같은 방 잠금(`pg_advisory_xact_lock(-방 id)`)을 잡음
  - 막기가 먼저면 뒤 예약은 409. 예약이 먼저면 막기 응답의 "겹친 예약" 목록에 나옴. 둘 다 빠져나가는 틈이 없음
  - 막기끼리 겹침은 DB 제약(`no_block_overlap`, 풀리지 않은 것만)이 막음 → 409 `ROOM_BLOCK_OVERLAP`
- **이미 잡힌 예약:** 바로 지우지 않고 목록으로 보여 줌. 관리자가 확인하면 시작 전(BOOKED) 예약만 취소 + 대표자·참여자 알림(한 트랜잭션, 메일은 커밋 뒤)
  - 사용 중인 예약은 취소가 안 되는 상태라(상태 트리거) 목록에 `cancelable: false`로 보이고, 필요하면 강제 퇴실로
- **인덱스 영향:** `room_block`의 EXCLUDE gist 인덱스(방 + 기간)를 예약 저장 때 확인에도 씀. 예약 저장에 쿼리 1번 늘어남(방 5개·막기 몇 줄이라 작음)
- **버린 것:** 막을 때 겹친 예약 자동 취소(관리자가 모르는 채로 학생 예약이 사라짐), 풀 때 줄 삭제(누가 언제 막았는지 기록이 없어짐)
- **보여 주기:** 빈방 조회 칸에 `block`(사유·메모·끝), 방에 `blockedNow`. 방 현황은 걸린 예약이 없고 막혀 있으면 `BLOCKED`(빈 방 수에서 빠짐)
  - 이유: 학생이 409를 받기 전에 화면에서 "점검 중"을 보게. 걸린 예약이 있으면 그 상태(IN_USE·RESERVED)를 먼저 보여 줌

## 22. 방의 사과: 장치 오류 노쇼 자동 무르기 (11/9 지영)

> Q-19. 문 장치가 끊겨서 못 들어간 학생이 노쇼 벌칙을 받지 않게. 번호 20·21은 core #97·#98

- **받는 것:** `POST /api/device-faults` (장치 토큰). 장치가 끊긴 동안 오류 구간과 그동안 눌린 번호를 모아 뒀다가 다시 연결되면 보냄 (모양은 수연 제안)
  - 같은 `eventId`는 한 번만 (센서 이벤트와 같은 `ON CONFLICT DO NOTHING`)
- **번호는 저장 안 함:** 받을 때 "같은 방, 그 번호, 번호가 맞을 수 있던 시간(시작 10분 전 ~ 입실 마감)" 예약을 찾아 id만 남김. 키패드 5번 잠금에도 안 셈
  - 이유: 번호는 문 여는 비밀이라 DB에 하나 더 남기면 위험만 늘어남
- **무르기:** 번호가 눌린 기록이 있는 `NO_SHOW` 예약에 `no_show_excused_at`. 상태는 `NO_SHOW` 그대로(기록·통계, 상태 트리거도 못 바꿈), 벌칙 세기(`suspendRepeatedNoShows`)에서만 뺌
  - 이 노쇼 뒤에 걸린 노쇼 정지는 풀어 줌(끝을 지금으로, 지금 막 시작한 건 지움). 다른 노쇼와 합쳐 걸린 정지여도 풂 → 장치 탓이 섞이면 학생 편
  - 푸는 건 이 노쇼를 센 정지 하나뿐(노쇼 뒤 처음 시작한 노쇼 정지). 그 정지가 이미 끝났고 다른 노쇼로 새 정지가 걸렸으면 새 정지는 그대로. 다른 정지 기간 안에 생긴 노쇼는 어느 정지에도 안 셌으니 아무것도 안 풂
  - 대표자·참여자에게 사과 알림(`DEVICE_APOLOGY`)
- **언제 무르나:** 요청은 저장만 하고 바로 응답. 무르기는 응답과 따로 도는 스레드 하나가 곧바로(몇 초 안) 함. 그게 실패하거나 서버가 내려가 못 돌면 1분 정리가 다시 무름(두 겹). 오류가 노쇼보다 먼저 와도 정리가 노쇼로 바꾼 직후 같은 정리에서 무름
  - 요청 안에서 무르지 않는 이유(11/9 지영 "안전하게 가자"): 번호가 맞을 때만 정지 풀기·알림 저장을 더 하면 응답이 조금 늦어져, 장치 토큰을 가진 사람이 시간 차이로 맞은 번호를 짐작할 수 있음. 요청은 맞든 안 맞든 저장 + "무르기 확인" 신호 하나만 함. 7e12285에서 맞음/틀림 응답 시간을 각 400번 재 p50 차이 10µs대(틀린 번호끼리 차이와 같음)
  - 1분 정리만 쓰지 않은 이유(11/9 지영 "학생이 1분 기다리는 것도 좀"): 사과가 최대 1분 늦음
  - 요청이 몰려도 기다리는 실행은 하나만 쌓음(스레드 1개). 무르기는 조건부 UPDATE라 정리와 겹쳐도 한 번만
- **동시성:** 무르기는 `no_show_excused_at IS NULL` 조건부 UPDATE라 정리가 겹쳐도 한 번만 (알림도 한 번)
- **인덱스 영향:** `device_fault_attempt (reservation_id)` 부분 인덱스, `device_fault (room_id, started_at)`. 예약·키패드 쓰기 길은 그대로
- **버린 것:** 번호 없이 시간만 겹치는 노쇼 자동 무르기(누구 예약인지 모름 → 관리자 목록은 다음 PR), "문 안 열림" 감지(지금 문은 LED만, 잠금장치 없음)

## 23. 빈방 릴레이 (11/9 지영 "기다리기도 그렇게 가자")

> Q-18. 20–22번은 #97·#98·#99에 있음. 마이그레이션 V24는 V21–V23 다음이라 그 셋이 먼저 머지돼야 함

- **규칙 5개:** 기다리기는 한 사람 동시에 3개(칸마다 팀 수 제한 없음, 선착순) · 취소되면 줄 첫 사람에게 5분 잡아 두기, "넘길게요"·5분 지나면 다음 사람 · 받기는 보통 예약(`relayOfferId`)이라 대표자·인원·친구·정지 규칙 그대로 · 시작 30분 전부터 취소된 자리는 넘기지 않고 그냥 빈 칸 · 받은 예약도 노쇼는 보통과 같음. 숫자 3·5·30은 `mspace.reservation.relay` 설정값
- **잡아 두기:** 별도 "가예약" 상태를 만들지 않고, 넘김(`relay_offer`)이 열려 있는 동안 예약 저장(`JdbcReservationAdapter.insert`) 한 곳에서 409 `RELAY_HELD`로 막음
  - 이유: 예약 상태를 늘리면 노쇼·겹침 제약·참여자 트리거·통계를 다 고쳐야 함. 저장 길이 하나라 새 예약·즉시 시작·연장이 모두 막힘
  - 동시성: 넘김 만들기와 예약 저장이 같은 방 잠금(`pg_advisory_xact_lock(-방)`)을 잡음. 같은 구간 열린 넘김은 DB 제약 `one_open_offer`로 하나뿐
  - 잠금 순서는 어디서나 방 → 넘김 줄(1분 정리의 5분 지남 처리도 방 잠금부터). 여러 방을 잡는 advance끼리는 고정 번호 잠금으로 한 줄, advance는 손댈 방을 먼저 모두 방 번호 순으로 잠근 뒤 넘김 행을 바꿈. 받기는 방 잠금 뒤 시각으로 5분을 다시 봄(`expires_at > now`)
  - 받기는 예약 저장과 넘김 `TAKEN`이 한 트랜잭션. 5분이 끝나는 순간 정리와 겹치면 조건부 UPDATE(`status = 'OPEN'`)라 한쪽만 됨 → 늦으면 409 `RELAY_OFFER_INVALID`
- **기다리기 3개:** 회원 잠금 안에서 세고 넣음(동시에 4개 눌러도 3개)
- **일부만 받으면:** 넘김 구간(14:00–15:00) 중 일부(14:00–14:30)만 받으면 남은 칸(14:30–15:00)을 그 칸 기다린 다음 사람에게 넘김. 받기 뒤 같은 방 잠금 안에서 끝나지 않은 예약이 안 덮은 부분만 계산하므로 받은 예약과 겹치지 않음
- **넘기기 시점:** 취소 커밋 뒤 바로(취소는 그대로 두고 넘기기만 따로 커밋, 실패하면 1분 정리가 "줄 선 사람이 있는데 넘김이 한 번도 없는 취소"를 찾아 다시), 넘길게요 뒤 바로, 5분 지남은 1분 정리. 알림은 알림함에 같은 트랜잭션, 바깥 채널은 커밋 뒤
- **인덱스 영향:** 예약 저장마다 `relay_offer` EXISTS 1번이 늘어남. 열린 넘김만 보는 gist 제약 인덱스를 탐(보통 0–몇 줄)
- **버린 것:** 대기 팀 수 제한(칸마다 N팀) — 지영이 "1인 3개"로 정함. 넘겨받은 사람에게 자동 예약 — 참여자·인원이 바뀌었을 수 있어 직접 받게 함

## 29. 두고 간 물건: 종류 구분 없이, 3시간 뒤 다시 확인해 경고 (11/10 10차 회의, 지영·수연)
- **2시간 → 3시간 (11/10 지영, #112 머지 뒤):** 다음 팀이 바로 이어 예약하면 앞 팀이 찾으러 올 틈이 없음. 다음 팀 입실 때 바로 경고하는 안은 노트북·폰처럼 실수로 두고 가는 경우에 너무 빡빡해서 버림. 대신 찾으러 올 시간을 3시간으로 늘림. `mspace.tidy.recheck-after-minutes` 120 → 180. 아래 "2시간"은 처음 결정 그대로 둠
- **무엇:** 방 카메라 결과를 `CLEAN` / `LEFT_ITEMS`(쓰레기 포함 "두고 감") 두 개로. 물건마다 `{name, confidence}`(모델 이름 영어 그대로, 확신도 0~1). 예약마다 `FIRST`(퇴실 직후)와 `RECHECK`(퇴실 + 2시간) 한 번씩
- **FIRST:** `LEFT_ITEMS`면 대표자·참여자에게 `LEFT_ITEM` 알림만. 신고는 안 만듦. 예전처럼 "치울 것 있음 → 바로 어질러짐 신고"를 남기면 쓰레기 하나로 경고가 두 번(바로 + 2시간 뒤) 갈 수 있어서 그 길은 없앰(`NEEDS_CLEANING`은 400, 지난 기록만 남음)
- **다시 확인 요청:** `GET /api/rooms/{id}/current`의 `recheck {reservationId, at}`. FIRST가 `LEFT_ITEMS`이고 RECHECK가 아직 없고, 지금 누가 방에 있지 않을 때만 준다. 장치는 `at`이 지나고 방이 비어 있으면 RECHECK를 보냄
- **RECHECK:** 확신도 `mspace.tidy.warn-min-confidence`(0.8) 이상 물건이 하나라도 남으면 core가 카메라 신고를 만들고 사람 없이 바로 사실로 정해(`judged_by` 없음) 그 예약 대표자에게 경고. 경고 세기·정지는 사람 신고 판정과 같은 길(`JudgeReportService`). 경고가 신고 번호를 꼭 가져야 해서(`user_warning.report_id NOT NULL`) 신고를 만듦
- **왜 core가 바로 정하나 (지영 "첫 번째로"):** AI 판정 연결부(Q-28, `WarningReviewer` 포트)는 아직 없음. 11/13 동결 전에 끝나는 길. 0.8은 모델 비교 결과를 보고 설정값만 바꿈
- **다음 팀이 2시간 안에 입실하면:** 다시 보지 않고 경고도 없음(다음 사람 물건과 섞여 판단할 수 없음 → "확인 불가 = 벌칙 없음"과 같은 셈). 사용 중이면 `recheck`를 안 주고, 나가면 `lastEnded`가 바뀌어 앞 예약은 `TIDY_CHECK_NOT_LATEST`
- **거절:** 시각 전 `409 TIDY_RECHECK_TOO_EARLY`, 다시 볼 것이 없거나 누가 방에 있으면 `409 TIDY_RECHECK_NOT_NEEDED`, 같은 단계 두 번 `409 TIDY_CHECK_EXISTS`
- **DB (V26):** `phase`, `confidences real[]`(items와 같은 길이, 0~1), 유니크를 `(reservation_id, phase)`로. 신고 증거는 FIRST 줄만 읽음(같은 유니크 인덱스). 동시성: 예약 줄 `FOR UPDATE`로 같은 예약의 FIRST·RECHECK가 한 줄로 섬, 유니크가 마지막 방어
- **안 한 것:** 빈 방·물건 사진 올리기(Q-27, 다음 PR), 가져가러 들어가는 방법(Q-27 결정 대기)

## 30. 찾으러 갈게요 10분 QR (11/10 지영 "찾으러 갈게요 누르면 10분 QR", "다음 팀이 쓰고 있어도 퇴실 뒤 3시간")
- **무엇:** `POST /api/reservations/{id}/retrieve-pass` → `{reservationId, roomId, code, qrText, expiresAt}`. 번호는 입실 번호와 같은 6자리, QR 글자도 `MSPACE:<방>:<번호>` 그대로라 문 앞 웹캠·키패드를 고칠 것이 없음
- **문 앞:** `POST /api/access/verify`가 예약 번호로 못 찾으면 찾으러 온 QR을 봄. 맞으면 `{"result":"OPENED","purpose":"RETRIEVE"}`(수연 요청). 체크인은 안 함. 장치는 RETRIEVE를 새 팀 입실로 보지 않으면 됨. 같은 eventId 재전송도 RETRIEVE 그대로(`access_event.purpose`)
- **받는 조건:** 그 예약의 대표자·참여자(두고 간 물건 알림을 받은 사람), 퇴실 직후 확인(FIRST)이 `LEFT_ITEMS`, 퇴실 뒤 `mspace.tidy.recheck-after-minutes`(180분) 안. 다음 팀이 방을 쓰고 있어도 줌
- **횟수:** 예약마다 살아 있는 QR은 하나. 10분 안에 다시 누르면(참여자가 눌러도) 같은 QR, 10분 안에는 문을 여러 번 열 수 있음. 지나면 3시간 안에서 다시 눌러 새 번호
- **거절:** 남의 예약·없는 예약 `404 RESERVATION_NOT_FOUND`(있는지 알려 주지 않음), 아직 사용 중 `409 RESERVATION_NOT_ENDED`, 두고 간 물건 없음 `409 RETRIEVE_NOT_NEEDED`, 3시간 지남 `409 RETRIEVE_TOO_LATE`
- **번호 겹침:** 같은 방의 끝나지 않은 예약 번호·살아 있는 QR과 겹치지 않게 뽑음. 남는 틈: QR을 준 뒤 10분 안에 같은 방 새 예약이 같은 번호를 받으면 문 앞에서는 예약이 먼저(100만분의 1 수준이라 둠)
- **동시성:** 예약 줄 `FOR UPDATE`로 대표자·참여자가 동시에 눌러도 QR 하나. 문 앞은 원래대로 방 잠금 줄로 한 줄
- **DB (V27):** `retrieve_pass`(예약·방·누가·번호·준 시각·끝 시각·처음 쓴 시각), `access_event.purpose`
- **안 한 것:** 경고 판단에 "찾으러 왔나(`first_used_at`)"를 쓰는 것, 다음 팀 입실 때 3시간 전이라도 RECHECK 받기(수연 장치 시험 뒤 결정)

## 31. 방 카메라 사진을 core에 30일 (docs Q-27, 11/10 10차 회의 "사람이 0명인 빈 방·물건 사진은 저장 가능", 같은 날 지영 "core에 올려 30일 보관")

- **11/11 추가: 입실 직전 빈 방 `ENTRY` (docs Q-27 수연 결정, v0.4.39):** 사람이 처음 보이기 직전 3초 동안 0명일 때 찍은 컬러 사진. 젯슨이 퇴실 뒤 `FIRST` 결과를 보낸 다음 같이 올려서 "마지막 퇴실 예약만" 규칙을 그대로 씀. 관리자 화면이 입실 전(`ENTRY`)·퇴실 뒤(`FIRST`·`RECHECK`)를 나란히 봄. V31로 `phase` CHECK에 추가(V30은 #118)

## 32. 경고 철회 요청: 7일 안 1번, 판단기가 다시 보고 core가 적용 (FR-RPT-105, Q-24 ①–③ 11/10 지영 "추천대로")
- **무엇:** `GET /api/penalties/me/warnings?days=30`(내 경고 + 요청 상태), `POST /api/warnings/{id}/appeal {text, evidence[]}` → 201 PENDING. 모양은 docs api 6-1(core #111 요청) 그대로, 400 코드는 core에 있는 `INVALID_REQUEST`
- **① 요청 중에도 센다:** 요청만으로 정지를 미루지 못하게. 철회될 때(`user_warning.withdrawn_at`)만 경고 수에서 빠짐
- **② 철회되면 그 경고로 걸린 정지를 지금 끝냄:** "그 경고가 센 정지" = 정지를 건 경고 id 이하 + 앞 정지 경계보다 뒤 + 정지 시작 30일 안에 받은 경고. 끝 시각을 지금으로 당기고 `lifted_at`을 남김. 푼 정지는 다음 집계 경계로 안 씀 → 남은 경고는 다시 셈(경고 3번 중 1번 철회 → 정지 풀리고 2회)
- **③ 확인 불가 = 철회:** 판단기가 "유지"라도 확신도가 `mspace.appeal.min-confidence`(0.8)보다 낮으면 철회. 판정의 "확인 불가 = 벌칙 없음"(FR-RPT-103)과 같은 셈, 관리자에게 넘기지 않음(무인). 기록에는 판단기가 낸 원래 확신도
- **판단 위치 (Q-24 ④, 영준 11/10):** core `WarningReviewer` 포트. 어댑터가 판단만 내고, 철회·정지 풀기·알림은 core가 함. 판단 기록(`warning_appeal`의 reviewer·prompt_version·confidence·evidence_used)도 core에 → 정답 세트로 판단기별 정확도 표
- **지금 판단기 = 규칙(`rules`, `rules-v1`):** 외부 AI 없이. 카메라 경고는 다시 확인 때 남은 물건의 가장 높은 확신도가 0.8 이상이면 유지, 아니면 철회. 학생 신고로 받은 경고는 글·사진을 읽지 못해 확신도 0 → 철회. Gemini 어댑터는 같은 포트 뒤에(키 필요, 지영 답 대기)
- **왜 따로 판단하나(1분마다):** AI 호출을 요청 트랜잭션 안에 두면 느린 응답 동안 경고 줄 잠금을 쥠. 요청은 저장만 하고, 판단은 트랜잭션 밖에서 → 결과 적용만 한 트랜잭션. 판단기가 실패하면 대기로 두고 다음 번에 다시
- **동시성:** 요청은 경고 줄 `FOR UPDATE` + `warning_appeal.warning_id` 유니크(두 번 눌러도 1건). 적용은 요청 줄 `FOR UPDATE`(대기일 때만) + 판정과 같은 회원 잠금(`lockUser`) → 판정이 3번째 경고를 세는 중에 철회가 끼어 숫자가 어긋나지 않음
- **사유 막기:** 10–500자, 숫자 7개 이상 이어지면(띄어쓰기·하이픈 허용) 학번·전화번호로 보고 400. 판단기(AI)에게 넘어가서
- **DB (V29):** `warning_appeal`(경고마다 1줄), `user_warning.withdrawn_at`, 두 정지 표의 `lifted_at`, 알림 종류 칸 20 → 30자(`WARNING_APPEAL_RESULT` 21자). 대기 요청 고르기용 부분 인덱스 `WHERE status = 'PENDING'`
- **인덱스·트래픽:** 요청은 경고 수만큼(하루 몇 건). 1분마다 대기 요청 최대 10건(`batch-size`)만 봄. 경고 세기 쿼리는 `withdrawn_at IS NULL` 조건만 늘어 기존 `user_warning_recent` 인덱스 그대로
- **안 한 것:** 관리자 대시보드 철회율·정확도, 관리자 경고 목록에 철회 표시, Gemini 어댑터

## 33. 경고 철회 판단기에 Gemini 붙이기 (FR-RPT-105, A-6, 11/10 지영 "규칙 판단기 먼저 → Gemini 다음", 키는 지영이 AI Studio 무료 키를 재웅에게)

- **트랜잭션·트래픽:** 판단은 #116처럼 트랜잭션 밖. 1분마다 최대 10건(`batch-size`)이라 무료 한도(분당 요청 수) 안. 요청 하나가 20초 넘게 걸려도 잠금을 쥐지 않음
- **같이 고친 것 (#116 영준 제안, Sonar S2583):** `tx.execute` 결과 `null` 비교 대신 `apply`가 `Optional`을 돌려줌
- **키:** 서버 `.env`의 `GEMINI_API_KEY`(재웅). 코드·채팅·GitHub에 안 씀. 설정 `toString`에도 안 찍힘
- **안 한 것:** 사진 보내기, 정답 세트로 rules vs Gemini 정확도 표, 젯슨 어댑터

## 35. 카메라만으로는 경고하지 않고 알림만 (FR-DEV-105·FR-RPT-103, 11/11 수연 정확도 측정, 11/11 지영 "그렇게하자")
- **왜:** 수연이 방 카메라 두고 간 물건 판정 정확도를 재 보니 51%. 깨끗한 방 16번 중 11번을 "물건 있음"으로 봄. 이 정도면 카메라만 보고 경고하면 억울한 경고가 절반 가까이 나옴
- **무엇:** 설정 `mspace.tidy.camera-warn`(기본 `false`)
  - 꺼져 있으면 3시간 뒤 다시 확인(`RECHECK`)에 물건이 0.8 이상 남아도 신고·경고를 만들지 않고 대표자·참여자에게 "물건이 아직 남아 있어요" 알림만 보냄
  - 신고 자동 판정(결정 34)에서도 어질러짐을 카메라만으로 사실로 정하지 않음 → 확인 불가(벌칙 없음)
  - 카메라 정확도가 오르면 `true`로 바꾸면 결정 33·34의 경고가 다시 켜짐. 코드는 그대로
- **"찾으러 갈게요" QR을 쓴 경우 (11/11 수연·지영):** 그 예약의 QR로 문을 한 번이라도 열었으면(`retrieve_pass.first_used_at`) 다시 봤을 때 물건이 보여도 경고 안 함. 찾아갔는데 카메라가 잘못 봤을 수 있어서. QR을 받기만 하고 안 열었으면 그대로
- **대안과 비교:** 수연 안 "관리자에게 확인 요청"은 무인 운영(11/10 회의)과 맞지 않아 알림만으로 정함. 경고 기준 확신도를 0.8에서 더 올리는 안은, 잘못 본 것도 확신도가 높게 나와 효과를 알 수 없어 정확도를 다시 잰 뒤에 정함
- **남은 것:** 다음 팀 입실 직전 다시 확인(수연 11/12 장치 시험 뒤), `camera-warn`을 켤 때 정할 것: 3시간째 다시 확인(RECHECK) 때 아직 열린 QR(2시간 59분에 받은 것)이 있으면 경고를 미룰지 (CodeRabbit #118, 꺼져 있으면 경고가 없어 지금은 생기지 않음)
- **같은 물건으로 두 번 벌하지 않음 (#118 재웅 리뷰):** 신고 자동 판정은 앞 팀의 다시 확인(`RECHECK`)이 있으면 그 결과를 먼저 봄(깨끗하면 확인 불가). 앞 팀이 같은 퇴실로 이미 카메라 경고(카메라 신고)를 받았거나 찾으러 갈게요 QR로 문을 열었으면 학생 어질러짐 신고도 확인 불가
- **어질러짐 신고는 앞 팀 퇴실 3시간 뒤에 판정 (11/11 지영 "3시간 뒤에 판정"):** 앞 팀은 퇴실 뒤 3시간(`mspace.tidy.recheck-after-minutes`) 안에 찾으러 갈게요 QR을 받아 10분(`retrieve-pass-minutes`) 동안 물건을 가져갈 수 있어서, 마지막 QR이 닫히는 퇴실 + 3시간 10분이 지나야 판정 (CodeRabbit #118). QR 사용도 같은 예약 행을 잠가서 경고와 동시에 확정되지 않음. 그 안에 찾아갔으면 확인 불가. 다음 팀 신고 + 퇴실 직후 카메라 0.8 이상이면 사실(지영 "신고+카메라면 경고", `camera-warn` 켜졌을 때만). 비품·창문 신고는 기다리지 않음. 신고한 학생은 결과를 최대 3시간 기다림
