## 1. 동시 100건에서 중복 예약 (11/2)

- **무엇이 안 됐나:** "비었나 조회 → 저장" 순서로만 막으면, 같은 방·같은 시간에 동시에 누른 요청이 둘 다 "비었음"을 보고 둘 다 저장돼요. 제약 없는 버전으로 5번 재 보니 5번 모두 중복(3–10건 저장)
- **원인:** 조회와 저장 사이에 다른 요청이 끼어들 틈이 있어요(경쟁 상태)
- **해결:** 겹침은 DB 제약 `no_room_overlap`(EXCLUDE), 대표자 1건은 부분 유니크 인덱스 `one_active_per_owner`로 막고, 제약 이름을 409로 바꿔요. 겹침 여부는 서버에서 미리 조회하지 않고 DB 제약만으로 판단해요. 서버 검사는 시간 단위·길이·인원 같은 입력 규칙을 400으로 빨리 알려 주는 용도예요
- **결과:** HTTP 동시 100건 → 201 1건, 409 99건, DB 1건 (4번 같은 결과, 약 0.5초). 같은 대표자 100건 → 1건

## 2. 교착 (deadlock, 40P01) (11/2)

- **무엇이 안 됐나:** 같은 참여자 2명이 들어간 100팀이 다른 방·같은 시간에 동시에 예약 → 500이 69건
- **원인:** 두 트랜잭션이 참여자 줄을 서로 다른 순서로 잡으면서 서로를 기다림. 참여자를 id 순으로 넣어도 남음
- **해 본 것:** 교착이면 다시 하기만 → 503 69건, 약 70초로 실패
- **해결:** 저장 전에 `pg_advisory_xact_lock`으로 줄 세우기(방 → 사람 id 순) + 그래도 나면 새 트랜잭션으로 다시(처음 1번 + 다시 2번, 총 3번 시도. `MAX_ATTEMPTS = 3`)
- **결과:** 201 1건, 409 99건, 500 0건, 약 1초

## 3. 잠금 대기 상한 오류를 Spring이 모름 (11/3)

- **무엇이 안 됐나:** 잠금을 3초 넘게 기다리면 끊기게 `lock_timeout`을 걸었는데, 끊길 때 503 대신 500이 나감
- **원인:** PostgreSQL 55P03을 Spring이 분류하지 못해 `UncategorizedSQLException`으로 옴 (테스트로 발견)
- **해결:** 어댑터에서 55P03이면 `CannotAcquireLockException`으로 바꿔서 교착과 같은 다시 하기 → 3번 다 넘으면 503 `RESERVATION_BUSY`
- **확인:** `LockTimeoutTest`

## 4. 잠금 대기 상한이 잠금마다 따로 걸림 (11/3, CodeRabbit 지적)

- **무엇이 안 됐나:** 방 1개 + 사람 여러 명 잠금에 각각 3초가 걸려, 한 번 시도가 3초를 넘김
- **원인:** `lock_timeout`은 잠금 하나마다 적용됨
- **해결:** 시도마다 기한을 두고, 잠금마다 **남은 시간만** 다시 걸기. 0ms는 "무제한"이라 남은 시간이 1ms 미만이면 바로 실패
- **결과:** 고치기 전 3.5초 → 후 2초 (`LockDeadlineTest`). 다시 하기 포함 전체 기한은 넣지 않음(최악 상한 × 3)

## 5. 같은 멱등 키 동시 요청 (11/3)

- **무엇이 안 됐나:** 비서가 같은 확인을 동시에 20번 보내면 409가 12건
- **원인:** 모두 "키로 만든 예약 없음"을 본 뒤 저장하고, 늦은 쪽은 제약(대표자 1건·키 유일)에 걸림
- **해결:** 409가 나면 키로 다시 찾아서, 그 사이 커밋된 처음 예약이 있으면 200으로 돌려줌
- **결과:** 201 1건, 200 19건

## 6. 번호 확인과 취소 사이 경쟁 상태 (11/3, CodeRabbit 지적)

- **무엇이 안 됐나:** 키패드가 번호를 읽은 뒤(시작 10분 전–시작 사이) 대표자가 취소하면, 체크인이 0줄인데도 문이 열림
- **원인:** 번호로 예약을 찾은 뒤 체크인 UPDATE(`BOOKED → IN_USE`, 조건부)를 하는데, 그 사이 취소가 커밋되면 UPDATE 조건(`status = 'BOOKED'`)에 안 맞아 0줄이 됨. 코드는 0줄인지 보지 않고 "찾았으니 연다"로 처리함
- **해결:** 체크인 UPDATE가 0줄이면 예약을 다시 읽어서 `IN_USE`일 때만 연다(이미 다른 키패드 입력으로 입실한 경우). 취소됐으면 거절
- **결과:** 취소가 끼어든 경우 문이 열리지 않음 (`KeypadEntryServiceTest`)

## 7. 잠긴 한 줄 때문에 정리 전체가 멈춤 (11/3)

- **무엇이 안 됐나:** 1분마다 도는 노쇼·자동 퇴실 정리가, 다른 트랜잭션이 잡고 있는 예약 한 줄을 기다리다 나머지 예약도 처리하지 못함
- **해결:** 대상 줄을 `FOR UPDATE SKIP LOCKED`로 고르고 조건부 UPDATE. 잠긴 줄만 건너뛰고 다음 분에 다시 처리. 잠금 대기 상한은 마지막 안전장치로 둠
- **확인:** `ReservationSweepTest.lockedRowDoesNotBlockSweep` (한 줄을 잠가 둔 채 정리 → 잠긴 줄은 건너뛰고 나머지는 처리, `Swept(1, 1)`)

## 8. 아주 짧은 즉시 시작이 끝나도 남음 (11/3)

- **무엇이 안 됐나:** 14:29에 누르고 14:30에 끝나는 즉시 시작은 입실 마감(14:39)이 끝보다 늦어서, 입실 안 하면 끝난 뒤에도 `BOOKED`로 남아 그 칸을 막음
- **해결:** 노쇼 조건을 `checkin_deadline < 지금 OR end_at <= 지금`으로
- **확인:** `InstantStartApiTest.shortInstantEndsBeforeDeadline` (14:30에 NO_SHOW, 다음 예약 201)

## 9. 정리가 실패하면 예약 만들기까지 실패 (11/3)

- **무엇이 안 됐나:** 예약 만들기 전에 정리를 한 번 돌리는데, 정리에서 DB 오류가 나면 예약 만들기까지 500
- **해결:** 정리는 부가 작업이라 오류를 잡아 경고 로그만 남기고 예약 만들기를 계속. 남은 예약이 막으면 409, 1분 정리가 다시 처리
- **확인:** `CreateReservationRetryTest.sweepFailureDoesNotBlockCreate`

## 10. 다른 종류 요청에 같은 멱등 키 (11/3, 재웅 리뷰)

- **무엇이 안 됐나:** 미리 예약에 쓴 키를 `/instant`로 보내면 처음 미리 예약이 200으로 재생됨
- **원인:** 같은 요청인지 비교할 때 종류(미리 예약 / 즉시 시작)를 보지 않음
- **해결:** 키로 찾은 예약에 `is_instant`를 담아 종류도 비교 → 다르면 409 `IDEMPOTENCY_KEY_REUSED`
- **확인:** `InstantStartApiTest.keyFromBookingIsNotReplayedAsInstant`
